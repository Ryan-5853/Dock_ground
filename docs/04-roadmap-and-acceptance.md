# 实施路线与验收门

原则：先建立可测的低延迟数据通路，再接触真实动力系统。每一阶段都必须有可重复
的证据和明确的退出条件，不能以“界面已经能看到了”作为进入下一阶段的依据。

## 阶段 0：技术基线

当前交付：

- 冻结后端实时外环、WebUI 边界、UDP 主链路和坐标语义。
- 定义 100 Hz 控制周期和端到端时延预算。
- 定义飞控协议未知时的适配器边界。
- 定义安全状态机、故障注入和阶段验收门。

退出条件：

- 文档评审通过。
- 确认飞控协议、Dronebridge 端口/模式、VRPN tracker 信息和 failsafe 负责人。

阶段 0 不依赖上述待定值即可完成；真实控制实现依赖它们。

## 阶段 1：C++ 骨架、仿真源和 WebUI

当前实现状态：核心纵切框架已完成并通过构建、单元测试、HTTP/WebSocket 和浏览器
deadman 联调；30 分钟浸泡和故障注入门尚未完成。

交付：

- CMake/C++20 工程，自包含的非阻塞 HTTP/WebSocket 服务。
- `IPoseSource` 仿真源和 `ICommandSink` 本地 UDP 回环 sink。
- 100 Hz 控制线程、固定缓冲区、指标直方图和异步日志。
- Vite/React/Three.js 页面：机体、目标、坐标轴、状态和延迟显示。
- VRPN 位姿/目标/链路状态的模拟数据。

验收门：

- 控制周期 p99 偏差 < 2 ms；截止期超时 < 0.1%。
- 模拟位姿到 UDP 回环发送的内部 p99 ≤ 5 ms。
- 浏览器掉帧、关闭或重连不影响控制线程周期和发送序号。
- 30 分钟浸泡无内存持续增长、无未处理异常、无队列增长。
- 前端仅从同源服务运行，无控制热路径 HTTP 请求。

## 阶段 2：真实 VRPN 与坐标标定

当前实现状态：已通过官方 `libvrpn` 连接 `MCAvatar@192.168.31.221:3883`，
接收约 110–125 Hz 的 Pos_Quat 数据；自动 sensor 选择、毫米换算、首样本 X/Y 原点、
首帧目标对齐和可配置轴变换已实现。`body1` 已明确为目标刚体，VRPN 原始 X/Y/Z
已通过单轴移动确认与地面站 X/Y/Z 一一对应；`body0` 用途、Z 地面基准和毫米比例
仍待确认。两机时钟偏差约 368 ms，来源时间戳在 NTP/PTP 验证前不参与龄期。
后端已发现 `body0/body1`，默认绑定 `body1 → aircraft-01`；前端绑定菜单支持
刚体热切换，并以新刚体首帧重建局部原点和目标。

交付：

- `libvrpn` 客户端、tracker URL/sensor ID 配置、断线重连。
- 右手 XYZ 位姿表示和可配置刚体变换，机头默认 `+X`。
- VRPN 样本龄期、丢帧、时间戳有效性和重连统计。
- 3D 显示实测动捕位姿和目标轨迹。
- `dock_ground_vrpn_probe` 诊断工具，用于列出 sensor、原始位置、四元数和实际频率。

验收门：

- 静置 10 分钟无 NaN/Inf，四元数保持归一化。
- 人工沿 X/Y/Z 单轴移动时显示方向正确，机头 `+X` 和绕 `+Z` 的偏航方向正确。
- 断网/恢复不会导致历史位姿重放，恢复后只接受新样本。
- 通过实际服务器时钟同步或保守到达时间口径，得到可解释的龄期。
- 控制线程不被 VRPN 断线阻塞。

## 阶段 3：ESP32-C5 透明链路

交付：

- 向 `192.168.31.100:<确认端口>` 的 UDP 发送器与接收器。
- 独立的应用层回环/回显协议，不依赖飞控协议。
- 序号、CRC、RTT、丢包、乱序、抖动统计。
- 必要时在串口侧加入 COBS/长度前缀分帧。
- 网络配置检查工具：RSSI、信道、端口、UDP 回显、串口参数。

验收门：

- 100 Hz 回环连续 30 分钟，序号可对账，无错误端口静默发送。
- 实际环境 UDP 单程 p95 ≤ 10 ms、p99 ≤ 25 ms，抖动可解释。
- 丢包/突发丢包不会造成内部排队；下行恢复后只使用最新样本。
- 拔掉 ESP32、AP 重启和链路恢复时状态机表现符合预期。
- 在确认 TCP/UDP 模式、串口波特率和报文边界之前，不得接入飞控动力输出。

若本门不达标，优先更换 AP/信道、调整 ESP32 功耗和分帧配置；不允许通过降低
控制频率来掩盖长尾后再进入飞行阶段。

## 阶段 4：飞控协议适配器与台架联调

交付：

- 按冻结的飞控线协议实现 `ICommandCodec` 和下行状态解析。
- 三轴位置 PID 和速度阻尼到四通道 roll/pitch/yaw-rate/throttle 映射、序号、过期帧拒绝和
  ACK 回显。
- 飞控模式/解锁/降落管理消息（协议支持时）。
- 飞控端超时和地面站端超时联合测试。

验收门（螺旋桨拆除）：

- 每个控制周期都能在飞控回显中匹配序号；CRC/版本错误被拒绝。
- 四元数轴系/符号验证，不是仅“界面看起来正确”。
- 拔网线、关闭地面站、杀掉后端、杀死 ESP32 电源，飞控均在约定时间内进入
  failsafe，且独立遥控器可以接管。
- 飞控拒绝旧序号、重复报文和非法推力。
- 管理操作具有 ACK/NACK，UI 状态与实际飞控状态一致。

## 阶段 5：位置环台架与系留测试

交付：

- 位置外环参数、目标限幅、推力映射和失效逻辑。
- 轨迹目标、速度摇杆、hold 与手动接管。
- 实际端到端延迟和闭环响应报告。

验收门：

- 使用实际地面站、AP、ESP32 和飞控，端到端 p95 ≤ 40 ms、p99 ≤ 80 ms，
  不达标不得进入自由飞行。
- 阶跃/斜坡目标响应无不可接受的超调、振荡和积分饱和。
- 动捕暂停、网络抖动、CPU 满载和浏览器断开时控制安全降级。
- 操作者独立遥控器始终可接管，地面站不能覆盖其优先级。
- 所有参数变更可追溯，报告包含日期、主机、网络拓扑和固件版本。

## 阶段 6：受控飞行与发布

只在阶段 1–5 全部通过且故障注入没有未解释项后进行。发布前：

- 固定 systemd 服务、只读配置、日志轮转和崩溃重启策略。
- 预置“禁止自动控制”“禁止自动 arm”“无动捕不发送”等硬门禁。
- 生成带版本号、配置校验和和协议版本号的发布包。
- 现场检查 AP 信道、RSSI、飞控 failsafe、遥控器接管和紧急处置流程。
- 保存完整链路日志和端到端延迟统计。

## 首批实现的优先级

1. 实时骨架、最新值覆盖、指标和仿真回环。
2. 真实 VRPN 接入和坐标标定。
3. ESP32 UDP 透明链路实测与故障注入。
4. 飞控协议适配器和台架 failsafe。
5. 位置环参数与飞行验证。

UI 的视觉细节不应阻塞前两项；但位姿、目标、链路状态和样本龄期必须在早期可见，
否则无法定位延迟来源。
